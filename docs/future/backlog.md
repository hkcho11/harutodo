# Future Backlog

작성일: 2026-06-02

현재 구현 범위는 인증, 커플 연결, 오늘 할 일, 월간 캘린더, 마이페이지, 투두/일정 입력 시트, 기본 Realtime/서비스 계층을 전제로 정리했다.
각 항목은 제품 검증에 필요한 순서대로 배치했으며, 실제 구현 전에는 Claude Code가 현재 코드 상태를 다시 확인해야 한다.

## P0: MVP 안정화

### 1. 핵심 플로우 수동 검수 체크리스트 정착

- 목적: 투두 CRUD, 일정 CRUD, 커플 연결, 파트너 동기화가 실제 모바일 사용 흐름에서 끊기지 않는지 확인한다.
- 범위: 검수 시나리오 문서화, 375px 기준 체크 항목, 로그인/비로그인/커플 미연결 상태별 기대 동작 정리.
- 검수 기준: 오늘 화면 진입 후 5초 안에 내 할 일과 파트너 할 일을 구분할 수 있어야 한다.
- 의존성: 없음.

### 2. 빈 상태와 에러 상태의 제품 문구 정리

- 목적: 사용자가 할 일이 없거나 연결/동기화가 실패했을 때 다음 행동을 바로 이해하게 한다.
- 범위: 오늘, 캘린더, 마이페이지, 커플 연결 화면의 빈/로딩/에러 문구와 CTA 기준 정리.
- 검수 기준: 빈 상태에서 주요 CTA가 1개로 명확해야 하며, 에러 상태는 재시도 또는 이동 경로를 제공해야 한다.
- 의존성: 디자인 시스템 문구 톤 확인.

### 3. 모바일 PWA 기본 품질 점검

- 목적: 설치형 앱처럼 사용할 때 하단 탭, safe area, 키보드, 스크롤이 깨지지 않게 한다.
- 범위: 375px, iOS Safari, Android Chrome 기준 레이아웃 검수 항목 정리.
- 검수 기준: 모든 주요 터치 타깃은 44px 이상이고, 하단 CTA가 키보드와 safe area에 가려지지 않아야 한다.
- 의존성: `PROJECT_RULES.md`의 PWA/모바일 기준.

### 4. 데이터 권한/RLS 회귀 검수

- 목적: 커플 공유 데이터가 다른 사용자에게 노출되지 않도록 출시 전 최소 보안 신뢰도를 확보한다.
- 범위: profiles, couple_groups, invite_codes, todos, events, custom_groups 기준 접근 가능/불가능 케이스 정리.
- 검수 기준: 미연결 사용자, 다른 커플 사용자, 로그아웃 사용자가 개인/커플 데이터를 조회하거나 변경할 수 없어야 한다.
- 의존성: Supabase 마이그레이션과 RLS 정책 확인.

## P1: 반복 사용성 고도화

### 1. 오늘 화면 정보 구조 개선

- 목적: 앱 첫 화면에서 "오늘 내가 해야 할 일"과 "파트너의 오늘 상태"를 더 빠르게 파악하게 한다.
- 범위: 내 할 일, 파트너 할 일, 함께 할 일의 우선순위와 완료 상태 표현 기준 정리.
- 검수 기준: 완료/미완료, 내 것/파트너 것/함께 할 일이 색상만이 아니라 텍스트나 아이콘으로도 구분되어야 한다.
- 의존성: 디자인 토큰과 기존 TodoSection/TodoItem 구조.

### 2. 일정과 투두의 관계 정리

- 목적: 사용자가 캘린더 일정과 날짜 기반 투두를 혼동하지 않게 한다.
- 범위: 일정은 시간/기간 중심, 투두는 완료 중심이라는 제품 규칙 정의.
- 검수 기준: 같은 날짜 화면에서 일정과 투두가 서로 다른 역할로 이해되어야 한다.
- 의존성: event/todo 도메인 타입과 입력 시트 UX.

### 3. 반복 입력 부담 감소

- 목적: 매일 쓰는 앱에서 같은 날짜, 같은 그룹, 같은 담당자를 반복 선택하는 비용을 줄인다.
- 범위: 최근 선택값 유지, 기본값 정책, 빠른 추가 UX 후보 정리.
- 검수 기준: 오늘 할 일 추가는 최소 입력으로 완료할 수 있어야 하며, 고급 옵션은 기본 흐름을 방해하지 않아야 한다.
- 의존성: Zustand 또는 로컬 UI 상태 정책.

### 4. 커플 연결 후 온보딩 보강

- 목적: 연결 직후 사용자가 무엇을 함께 관리하면 되는지 바로 알게 한다.
- 범위: 첫 연결 성공 화면, 첫 할 일 추가 CTA, 파트너 표시 확인 UX 정리.
- 검수 기준: 연결 성공 후 다음 행동이 하나로 명확해야 한다.
- 의존성: coupleService, CoupleProvider.

## P2: 제품 확장 후보

### 1. 반복 투두

- 목적: 집안일, 약속 준비, 루틴처럼 반복되는 커플 과제를 쉽게 생성한다.
- 범위: 매일/매주/매월 반복 후보, 종료 조건, 예외 날짜 정책 검토.
- 검수 기준: 반복 규칙이 복잡해져도 오늘 화면의 단순함을 해치지 않아야 한다.
- 의존성: 스키마 변경과 반복 인스턴스 생성 정책 사용자 승인 필요.

### 2. 알림과 리마인더

- 목적: 중요한 투두/일정을 놓치지 않게 한다.
- 범위: PWA Push 가능성, 로컬 알림 대안, 파트너 알림 범위 검토.
- 검수 기준: 알림 권한 요청은 사용자가 필요성을 이해한 순간에만 노출해야 한다.
- 의존성: 브라우저별 PWA Push 제약 확인, 별도 승인 필요.

### 3. 완료 기록과 주간 회고

- 목적: 커플이 함께 해낸 일을 가볍게 확인해 장기 사용 동기를 만든다.
- 범위: 완료 수, 함께 완료한 일, 주간 요약 후보 정리.
- 검수 기준: 생산성 대시보드처럼 무겁지 않고 하루투두의 실용적 톤을 유지해야 한다.
- 의존성: 완료 이력 보존 정책.

### 4. 커스텀 그룹 고도화

- 목적: 커플별 생활 패턴에 맞게 할 일을 분류한다.
- 범위: 그룹 순서 변경, 색상/아이콘 선택, 삭제 시 기존 투두 처리 정책.
- 검수 기준: 그룹 관리가 투두 추가보다 더 큰 흐름이 되면 안 된다.
- 의존성: customGroupService, 디자인 토큰 기반 색상 정책.

## Hold: 지금은 보류

### 1. 다인원 그룹 확장

- 보류 이유: 현재 핵심 가치는 2인 커플/부부 사용성이다. 다인원 구조는 권한, UI, 데이터 모델을 크게 바꾸므로 MVP 이후 별도 제품 검증이 필요하다.

### 2. 채팅/댓글 기능

- 보류 이유: 커뮤니케이션 앱으로 확장되면 핵심 가치가 흐려질 수 있다. 할 일 또는 일정에 꼭 필요한 맥락 메모 수준부터 검증하는 편이 안전하다.

### 3. 복잡한 생산성 기능

- 보류 이유: 우선순위 매트릭스, 프로젝트, 하위 작업 등은 개인 생산성 도구 성격이 강하다. 하루투두는 커플의 일상 공유 투두에 집중한다.

### 4. 과한 감성 연출

- 보류 이유: 서비스 방향은 실용적인 공유 투두/캘린더다. 장식적 인터랙션보다 명확한 구분, 빠른 입력, 안정적인 동기화가 우선이다.
