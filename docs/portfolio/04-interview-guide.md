# 하루투두 면접 가이드

## 1분 소개

하루투두는 커플 두 사람이 오늘의 할 일과 일정을 함께 관리하는 모바일
PWA입니다. 결혼을 준비하며 여자친구와 사용할 앱을 찾았지만 유료이거나
필요한 기능이 부족해, 두 사람이 직접 요구사항을 논의하고 개발했습니다.
메신저와 개인 캘린더에 생활 정보가 흩어지는 문제를 해결하기 위해 함께,
본인, 파트너 담당을 한눈에 구분하는 흐름을 설계했습니다.

저는 제품 범위와 UX 원칙, 기술 제약과 완료 조건을 정의하고 AI 개발 도구로
탐색과 구현 속도를 높였습니다. 생성된 결과는 권한, 데이터 정합성, 모바일
UX와 production build까지 직접 검증했습니다. 이 방식으로 6월 초 개발을
시작해 약 2주 만에 배우자와 실사용을 시작했습니다. 특히 Realtime 채널
누적 문제를 수명주기 관점에서 해결하고, 정합성을 보장할 수 없는 네이버
캘린더 연동은 구현 후에도 제거했습니다.

## 기술 개념 설명

### RLS란?

PostgreSQL이 각 행에 대한 접근 가능 여부를 사용자별 정책으로 판단하는
기능이다. 하루투두에서는 인증 사용자 ID가 해당 `couple_id`의
`user1_id` 또는 `user2_id`인지 확인한다. 프론트엔드 요청을 변조해도
DB가 다른 커플의 행을 거부한다.

### `created_by`와 `assignee_id`를 왜 분리했나?

만든 사람과 담당자는 다를 수 있기 때문이다. 내가 파트너의 할 일을 만들
수도 있다. 생성자는 감사와 권한 검증에 사용하고, 담당자는 UI 분류와 알림
수신자 결정에 사용한다. `assignee_id = null`은 함께 하는 항목을 뜻한다.

### Realtime은 어떻게 동작하나?

PostgreSQL의 행 변경이 Supabase Realtime 채널로 전달된다. 클라이언트는
`couple_id` 필터로 구독하고, INSERT·UPDATE·DELETE payload를 ID 기준으로
로컬 목록에 반영한다. 마운트 시 구독하고 언마운트 시 채널을 제거한다.

### 왜 구독 직후 다시 조회하나?

최초 fetch가 끝난 뒤 subscribe가 완료되기 전 변경이 발생하면 조회 결과와
실시간 이벤트 모두에서 빠질 수 있다. `SUBSCRIBED` 상태 직후 refetch하면
이 짧은 경쟁 구간을 보완할 수 있다.

### Service Worker의 역할은?

페이지와 별개로 브라우저가 관리하는 worker다. 정적 자산 캐시와 Push
이벤트를 처리할 수 있다. 하루투두에서는 Push를 시스템 알림으로 표시하고,
알림 클릭 시 기존 창을 관련 URL로 이동시키거나 새 창을 연다.

### pg_cron과 Edge Function을 왜 나눴나?

pg_cron은 “언제 실행할지”를 담당하고 Edge Function은 “누구에게 어떤
알림을 보낼지”를 처리한다. DB 트랜잭션 안에서 외부 Web Push 요청을 직접
보내지 않아 데이터 변경과 네트워크 실패를 분리한다.

### Zustand에는 무엇을 넣어야 하나?

여러 화면에서 공유되는 클라이언트 상태에 사용한다. 서버가 원본인 투두와
일정을 무조건 Zustand에 복제하면 Supabase 조회·Realtime·로컬 캐시 사이의
동기화 원천이 늘어난다. 하루투두는 데이터 조회와 구독을 Hook에 두고,
사용자·커플 컨텍스트와 UI 상태를 Store로 관리한다.

## 예상 질문과 답변 방향

### 왜 네이티브 앱이 아니라 PWA인가요?

MVP에서 하나의 코드베이스로 빠르게 배포하고 실제 커플 사용 흐름을
검증하는 것이 우선이었다. 설치와 Push가 필요해 일반 반응형 웹보다 PWA를
선택했다. iOS 백그라운드 기능과 앱스토어 유통 제약은 인지하고 있다.

### 구현한 네이버 캘린더 연동을 왜 제거했나요?

PWA의 홈 위젯 제약을 보완하려고 네이버 OAuth, 토큰 갱신, 일정 자동 등록까지
구성했다. 하지만 공개 API가 일정 추가만 지원해 하루투두의 수정·삭제와
네이버의 역방향 변경을 동기화할 수 없었다. 생성 시점에는 같아 보여도
시간이 지나면 서로 다른 일정을 보여줄 수 있었다.

일정 관리 서비스에서 이 차이는 사용자 신뢰를 훼손한다고 판단했다. 이미
구현했더라도 유지하지 않고 UI, API, 서비스와 개발·운영 DB의 토큰 테이블까지
제거했다. 이 경험 이후 외부 연동은 구현 전에 CRUD 범위와 데이터 식별·실패
복구 전략부터 확인한다.

### PWA에서 홈 위젯은 어떻게 제공했나요?

네이버 연동과 분리해 Scriptable 스크립트가 하루투두의 인증된 월간 일정·
오늘 할 일 API를 직접 조회하도록 구성했다. 외부 서비스에 데이터를 복제하지
않으므로 하루투두 DB가 계속 단일 원본이다. 갱신 토큰은 Keychain에 저장하고
API에서는 사용자와 커플 권한을 확인한다.

스크립트는 5분 뒤 갱신을 요청하지만 실제 시점은 iOS가 결정하므로 실시간이
아니라 지연 반영 방식이다. 즉 정합성은 유지하되 갱신 주기와 최초 설치
편의성을 트레이드오프로 받아들인 선택이다.

### 왜 Firebase가 아니라 Supabase인가요?

관계형 데이터와 DB 제약, SQL, RLS가 커플 멤버십과 일정·투두 관계를
표현하기 적합했다. Auth, Realtime, Edge Function을 한 플랫폼에서 빠르게
구성할 수 있다는 것도 MVP에 유리했다.

### RLS가 있으면 API Route는 필요 없나요?

단순 사용자 데이터 CRUD는 RLS가 적용된 브라우저 클라이언트로 처리할 수
있다. 하지만 서버 비밀정보나 높은 권한이 필요한 작업은 Route Handler
또는 Edge Function에 두고, 요청 사용자의 권한을 다시 검증해야 한다.

### 가장 어려웠던 문제는 무엇인가요?

Realtime 채널 누적이다. 증상은 캘린더가 멈추는 UI 문제였지만 원인은
클라이언트 인스턴스와 구독 cleanup의 수명주기 불일치였다. 싱글턴
클라이언트, 공통 구독 서비스, unique 채널명, cleanup으로 해결했다.

### AI가 만든 코드를 어떻게 신뢰했나요?

AI의 결과를 신뢰 대상으로 두기보다 검증 대상으로 다뤘다. 변경 전에는
요구사항·수정 범위·금지 사항·완료 조건을 문서화하고, 변경 후에는 lint,
type-check, build와 31개 반응형 화면 조건을 확인했다. 권한과 동시성은
UI 동작만 보지 않고 migration과 RLS 정책을 대조했다. 현재 부족한 핵심
사용자 흐름 통합 테스트는 기술 부채로 구분하고 있다.

### 본인이 직접 한 일은 무엇인가요?

실사용자와 문제 정의, MVP 범위, 사용자 흐름, 디자인 방향, 구현 우선순위,
완료 조건과 출시 여부를 결정했다. AI는 저장소 탐색, 변경 영향 분석과
여러 계층의 구현 반복을 가속했다. 최종 결과의 데이터 신뢰성, 기존 기능
영향과 모바일 UX는 직접 확인했고, 네이버 연동처럼 기준을 충족하지 못한
기능은 이미 구현했어도 제거했다.

### 기술을 이해하지 못하고 AI에 의존한 것 아닌가요?

AI가 구현 속도를 높이는 것과 기술 판단을 이해하는 것은 별개의 책임이라고
본다. 프로젝트 코드를 기준으로 RLS와 DB 제약, 트랜잭션과 동시성,
React effect cleanup, Realtime 구독 수명주기, OAuth 토큰과 PWA 동작을
학습하고 설명 가능 범위를 넓히고 있다. 모르는 부분을 아는 것처럼 말하지
않고, 구현 근거와 검증 결과를 확인한 범위에서 답한다.

### 다시 만든다면 무엇을 바꾸겠나요?

초기에 도메인 service 경계를 더 엄격히 두고, 커플 연결·RLS·Realtime을
포함한 통합 테스트 harness를 먼저 만들겠다. 또한 사용자 행동 지표와
알림 성공률을 초기부터 관찰해 기능 판단을 실제 사용 데이터에 연결하겠다.

## 면접 전 체크리스트

- [ ] 핵심 흐름을 실제 화면으로 3분 안에 시연할 수 있다.
- [ ] 시스템 구성도를 보지 않고 설명할 수 있다.
- [ ] 주요 테이블 관계와 RLS를 설명할 수 있다.
- [ ] Realtime lifecycle을 코드 위치와 함께 설명할 수 있다.
- [ ] 알림 예약부터 클릭까지의 흐름을 설명할 수 있다.
- [ ] AI 활용 방식과 본인의 책임 범위를 정직하게 말할 수 있다.
- [ ] 기술 부채 3개와 개선 우선순위를 말할 수 있다.
- [ ] 사용자 또는 성과 수치를 근거 없이 과장하지 않는다.
