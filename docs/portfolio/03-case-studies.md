# 하루투두 핵심 사례 연구

## 사례 1. 커플 연결의 권한과 동시성

### 문제

초대 코드는 인증된 두 사용자를 하나의 공유 데이터 경계로 연결한다.
코드가 동시에 여러 번 사용되거나 사용자가 여러 커플에 속하면 모든
공유 데이터의 권한 전제가 무너진다.

### 선택

- 한 사용자는 하나의 커플에만 속하도록 양쪽 사용자 컬럼에 unique index 적용
- 클라이언트의 `couples` 직접 INSERT 권한 제거
- 초대 코드 사용을 `SECURITY DEFINER` DB 함수로 제한
- `UPDATE ... RETURNING`으로 미사용 코드를 원자적으로 선점
- unique 충돌 시 코드의 `used_at`을 되돌리고 명시적 오류 반환
- 함수의 `search_path`를 고정해 객체 이름 가로채기 위험 축소

### 대안과 트레이드오프

- 애플리케이션 서버에서만 검사: 구현은 익숙하지만 우회 요청과 동시성에 취약하다.
- `SELECT FOR UPDATE`: 명시적 잠금도 가능하지만 코드 선점은 조건부 UPDATE 한 번으로
  상태 변경과 성공 여부를 함께 얻을 수 있다.
- 일반 INSERT 허용 후 RLS 검사: 멤버십 생성 규칙이 여러 클라이언트에 분산된다.

### 면접에서 설명할 핵심

RLS는 “어떤 행에 접근할 수 있는가”를, unique/check/FK는 “어떤 상태가
DB에 존재할 수 있는가”를 보장한다. 둘은 목적이 다르므로 함께 필요하다.

## 사례 2. Realtime 데이터 일관성과 수명주기

### 문제

실시간 구독은 연결만 하면 끝나는 기능이 아니다.

- 최초 조회와 구독 시작 사이에 발생한 변경을 놓칠 수 있다.
- 같은 화면 또는 Hook이 재마운트되면 중복 채널이 생길 수 있다.
- 자신의 mutation이 Realtime으로 다시 돌아오며 중복 반영될 수 있다.
- DELETE payload에 필요한 컬럼이 없으면 RLS 평가나 로컬 제거가 어려울 수 있다.

### 선택

- 커플 범위 구독을 `subscribeCoupleTable`로 공통화
- 모든 구독에 `couple_id` server-side filter 적용
- 실제 채널 이름에 unique suffix를 붙여 인스턴스 충돌 방지
- `SUBSCRIBED` 직후 refetch하여 fetch-subscribe gap 보완
- 호출 Hook에서 ID 기반 merge/filter로 이벤트를 멱등 처리
- cleanup에서 채널 제거
- 대상 테이블에 `REPLICA IDENTITY FULL` 적용

### 대안과 트레이드오프

- 이벤트 수신마다 전체 refetch: 단순하고 안전하지만 요청량과 화면 갱신 비용이 크다.
- payload만으로 항상 로컬 변경: 빠르지만 누락, 순서 역전, 중복에 더 신중해야 한다.
- 중앙 전역 채널 하나: 연결 수는 줄지만 여러 도메인의 캐시 무효화 책임이 복잡해진다.

### 면접에서 설명할 핵심

하루투두는 서버 상태를 Zustand에 복제하기보다 Hook이 조회와 구독을
관리한다. Zustand는 사용자·커플 컨텍스트 등 여러 화면에서 필요한
클라이언트 상태에 사용한다.

## 사례 3. 이벤트 기반 예약 알림

### 문제

일정 알림은 일정 생성 시 한 번 예약하는 것으로 끝나지 않는다. 일정 시간,
담당자, 사용자별 사전 알림 시간이 바뀔 수 있고 삭제·중복 발송·실패도
고려해야 한다.

### 선택

- 일정 INSERT/UPDATE를 DB 트리거가 감지
- UPDATE 시 기존 미발송 예약을 취소하고 재생성
- KST 일정 시간을 `TIMESTAMPTZ`로 변환해 저장
- 사용자별 알림 설정과 담당자를 기준으로 수신자 결정
- 부분 인덱스로 미발송 예약 조회 최적화
- pg_cron이 Edge Function을 5분 또는 15분 간격으로 호출
- Edge Function이 Push Subscription을 조회해 Web Push 발송
- Service Worker가 알림 클릭을 관련 화면과 날짜로 연결

### 대안과 트레이드오프

- 브라우저 타이머: 앱이 닫히면 신뢰할 수 없다.
- 일정 생성 API에서만 예약: DB가 다른 경로로 변경되면 예약과 일정이 어긋난다.
- 외부 작업 큐: 확장성은 좋지만 현재 2인 제품 MVP에는 운영 복잡도가 크다.

### 면접에서 설명할 핵심

DB 트리거를 사용한 이유는 일정과 예약의 정합성을 같은 데이터 변경 경계에
두기 위해서다. 반면 외부 네트워크 발송은 트랜잭션 안에서 처리하지 않고
Edge Function에 분리했다.

## 사례 4. 모바일 PWA UX

### 문제

커플 투두는 짧고 자주 확인하므로 데스크톱 중심의 복잡한 폼보다 설치,
재진입, 한 손 조작이 중요하다.

### 선택

- 375px를 기본 검수 폭으로 설정
- 44px 최소 터치 영역과 safe-area inset 반영
- 생성·편집을 바텀시트로 통일
- 날짜와 월 이동에 스와이프와 버튼을 함께 제공
- manifest와 Service Worker로 홈 화면 설치 및 Push 지원
- 알림 클릭 시 관련 날짜로 이동하는 딥링크 구성

### 트레이드오프

PWA는 하나의 웹 코드베이스로 배포하기 빠르지만 iOS 기능 지원과 백그라운드
동작에 제약이 있다. 현재 단계에서는 앱스토어 배포보다 빠른 반복과 실제
사용 검증을 우선했다.

## 사례 5. 네이버 캘린더 연동의 구현과 제거

### 문제

PWA에서 네이티브 홈 위젯을 직접 제공하기 어려워 기존 네이버 캘린더의
위젯을 활용하고자 했다. 하루투두 일정을 네이버에도 자동 등록하면 앱을
열지 않고 일정을 확인할 수 있다고 판단했다.

### 구현했던 범위

- 마이페이지에서 네이버 OAuth 연결 상태 조회와 연결·해제 제공
- authorization code를 access·refresh token으로 교환
- 사용자별 토큰과 만료 시각을 RLS 적용 테이블에 저장
- access token 만료 5분 전 refresh
- 일정 생성 성공 후 네이버 등록을 fire-and-forget으로 호출
- 제목, 기간, 시간과 장소를 iCalendar 형식으로 변환해 등록

### 검증 후 발견한 한계

공개된 캘린더 API는 일정 추가 엔드포인트만 제공했다. 하루투두 일정의
수정·삭제를 네이버에 반영할 수 없고, 네이버에서 바뀐 내용을 하루투두로
가져올 수도 없었다. 또한 두 서비스의 동일 일정을 연결하는 외부 ID도
관리할 수 없어 생성 이후 정합성을 유지할 수 없었다.

fire-and-forget은 외부 API 실패가 하루투두의 일정 생성을 막지 않는 장점이
있지만, 실패를 사용자가 알 수 없고 재시도·보상 처리도 없었다. 이 방식은
핵심 일정 데이터의 신뢰성을 요구하는 기능에는 부족했다.

### 선택

- 정합성을 보장할 수 없는 네이버 연동을 제품에서 제거
- 마이페이지 연결 UI와 관련 서비스 import 제거
- connect, callback, status, create-event, disconnect Route 제거
- 개발·운영 DB에서 OAuth 토큰 테이블과 RLS 정책 제거
- 환경 변수와 생성 경로에 남은 참조 점검

### 면접에서 설명할 핵심

기능을 구현한 사실보다, 검증 과정에서 제품 기준에 맞지 않음을 인정하고
제거한 판단이 핵심이다. 외부 연동을 시작하기 전에 CRUD 범위, 변경 이벤트,
외부 ID, 재시도와 실패 가시성을 먼저 확인해야 한다는 교훈을 얻었다.

## 사례 6. Scriptable을 이용한 iOS 홈 위젯

### 문제

네이버 연동을 제거해도 PWA만으로 iOS 네이티브 Widget Extension을 직접
만들 수 없다는 제약은 남았다. 앱을 열지 않고 홈 화면에서 일정과 오늘 할
일을 빠르게 확인할 수단이 필요했다.

### 선택

- Scriptable에서 실행되는 캘린더 위젯 스크립트 구성
- 인증된 `/api/widget/month`와 `/api/widget/today` Route Handler 제공
- 사용자 JWT로 커플 멤버십을 확인하고 RLS가 적용된 데이터만 조회
- 장기 세션을 위해 갱신 토큰을 iOS Keychain에 저장
- 월간 일정과 미완료 투두 표시를 위젯 크기별로 구성
- 위젯 탭 시 하루투두 캘린더 화면으로 이동
- `refreshAfterDate`로 5분 뒤 갱신 요청

### 네이버 연동과 다른 점

외부 캘린더에 일정 복사본을 만들지 않는다. Scriptable이 하루투두 API에서
원본 데이터를 읽기 때문에 별도의 수정·삭제 동기화나 일정 ID 매핑이
필요하지 않다. 위젯은 조회 전용 표현 계층이고 데이터의 단일 원본은
하루투두 DB에 유지된다.

### 트레이드오프

Scriptable을 설치하고 최초 설정을 해야 하므로 네이티브 내장 위젯보다
진입 장벽이 있다. 또한 `refreshAfterDate`는 실행 시점을 보장하는 타이머가
아니며 실제 갱신은 iOS가 결정한다. 따라서 실시간 동기화라고 표현하지 않고,
일정 시간이 지나면 최신 데이터가 반영되는 보조 조회 수단으로 정의했다.

### 면접에서 설명할 핵심

Scriptable은 네이버 연동의 이름만 바꾼 대안이 아니다. 데이터를 다른
서비스에 복제하는 구조를 버리고, 하루투두를 단일 원본으로 유지한 채
조회 화면만 확장한 설계다. 실시간성이 제한되더라도 정합성과 권한 체계를
유지하는 쪽을 선택했다.
