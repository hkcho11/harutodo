# 하루투두 포트폴리오 원고 초안

## Hero

### 하루투두

AI와 협업해 약 2주 만에 실사용으로 전환한 커플 공유 투두·캘린더 PWA

> 구현 생산성은 AI로 높이고, 제품 목표·사용자 흐름·기술 제약·완료 조건과
> 최종 검증은 직접 책임졌습니다.

- 역할: 제품 기획, UX/UI 설계, 프론트엔드, 백엔드·DB, 배포·운영
- 플랫폼: iOS Safari, Android Chrome, PWA
- 기술: Next.js, TypeScript, Supabase, PostgreSQL, Realtime, Web Push
- 기간: 2026.06 ~ 현재
- 실제 사용: 2026년 6월 중순부터 배우자와 지속 사용
- 실행 결과: 6월 초 개발 시작 후 약 2주 만에 실사용 시작
- 서비스 링크: `[공개 범위 확인 필요]`

## Background

### 결혼 준비의 계획이 여러 앱으로 흩어지는 문제에서 시작했습니다

결혼을 준비하며 일정과 해야 할 일이 동시에 늘어났습니다. 캘린더와 To-do
앱을 각각 사용하면서 여러 앱을 번갈아 확인해야 했고, 서로 연결된 계획이
분리되어 무엇을 언제 해야 하는지 한눈에 파악하기 어려웠습니다.

여러 서비스를 직접 사용해 봤지만 유료이거나 두 사람에게 필요한 기능이
부족했습니다. 그래서 커플이 일정과 할 일을 한 서비스 안에서 공유하고
관리하는 흐름을 함께 논의해 직접 제품을 기획하고 개발했습니다.

하루투두는 기능을 많이 제공하는 대신 다음 경험에 집중했습니다.

1. 앱을 열면 오늘 해야 할 일을 바로 본다.
2. 함께·나·파트너 담당을 즉시 구분한다.
3. 한 사람이 바꾼 내용이 다른 사람에게 바로 반영된다.

## Product decisions

### 두 명이라는 제약을 제품의 장점으로 사용했습니다

범용 팀 도구를 만들지 않고 `couples`를 정확히 두 명으로 제한했습니다.
이 결정으로 복잡한 조직·역할 관리 없이 함께, 본인, 파트너라는 세 가지
생활 언어를 UI와 데이터 모델 전체에 일관되게 적용할 수 있었습니다.

### 홈의 우선순위는 관리보다 파악입니다

홈 화면은 오늘 날짜, 완료 진행률, 지난 미완료 항목, 담당자별 투두 순으로
구성했습니다. 날짜 이동은 버튼과 스와이프를 함께 지원하고, 주요 추가
행동은 하단 FAB와 바텀시트로 처리해 모바일 한 손 사용을 고려했습니다.

### 커플 감성보다 반복 사용의 부담을 줄였습니다

장식적인 소셜 기능 대신 일정, 투두, 알림, 개인 주기 기록에 집중했습니다.
색상은 함께·본인·파트너의 의미를 모든 화면에서 동일하게 유지하고,
디자인 토큰으로 대비와 일관성을 관리했습니다.

## Real user feedback

### 현재 구현에서 확인된 가치

함께 서비스를 사용하는 파트너는 캘린더와 To-do를 여러 앱에서 따로
확인하지 않아도 되는 점, 개인·공동 To-do를 같은 서비스에서 관리하는 점,
필요한 개인 주기를 캘린더에서 확인하는 점과 정보 위계가 분명한 UI를
긍정적으로 평가했습니다.

이 피드백은 기능 수보다 반복 확인의 부담을 줄이겠다는 초기 제품 방향이
실사용에서도 유효했다는 근거로 사용합니다.

### 사용자 요청에서 만든 제품 백로그

- 일정과 To-do의 직접 연결
- 장보기·결혼 준비 체크리스트 같은 공동 To-do 템플릿
- 계약서·보험 증권·차량 서류를 위한 공동 문서 보관함
- 일정과 문서 연결 및 카메라 스캔
- 생활비·예산·공동 구매 내역을 관리하는 공동 자산 기능

위 항목은 아직 구현되지 않았으며 사용자 요청 단계의 백로그입니다.

### 문서 기능 구현 전 확인할 기술 조건

문서는 고위험 개인정보이므로 단순 업로드 기능부터 만들지 않습니다.
커플·소유자별 접근 권한과 관계 해제 시 권한 회수, 비공개 저장과 암호화,
짧은 만료 링크, 악성 파일 검사, 접근 기록과 삭제·보존 정책이 먼저
정의되어야 합니다.

스캔과 OCR을 추가할 때는 명시적 동의, 최소 수집, 민감정보 마스킹,
처리 후 원본 이미지의 보존 여부까지 완료 조건에 포함합니다.

## Architecture

### 편리한 실시간 공유와 안전한 데이터 경계를 함께 설계했습니다

Next.js PWA는 사용자 인터페이스와 서버 Route Handler를 담당합니다.
Supabase Auth가 사용자를 인증하고 PostgreSQL의 RLS가 해당 사용자가
`couple_id`의 실제 구성원인지 검사합니다. Realtime은 같은
`couple_id`의 변경만 구독합니다.

권한을 화면의 조건문에만 의존하지 않았습니다. 사용자가 브라우저 요청을
변조하더라도 다른 커플의 데이터를 읽거나 수정하지 못하도록 최종 권한
검증을 DB에 두었습니다.

## Case study 1

### 동시에 같은 초대 코드를 사용해도 한 번만 연결되도록 만들었습니다

초기 구현은 코드를 읽고 커플을 만든 뒤 사용 완료로 바꾸는 순서였습니다.
동시에 두 요청이 들어오면 같은 코드가 중복 사용될 가능성이 있었습니다.

이를 `UPDATE ... RETURNING`으로 유효한 코드를 먼저 원자적으로 선점하도록
변경했습니다. 사용자당 하나의 커플만 허용하는 unique index를 추가하고,
충돌이 발생하면 예외 처리에서 코드 사용 상태를 되돌렸습니다.

이 경험을 통해 UI 검증과 DB 무결성은 서로 대체 관계가 아니며, 동시 요청을
고려한 최종 제약은 데이터베이스에 있어야 한다는 점을 배웠습니다.

## Case study 2

### Realtime 채널 누적으로 발생한 캘린더 멈춤을 수명주기 문제로 해결했습니다

실시간 기능을 추가한 뒤 화면 이동과 재렌더링 과정에서 채널 인스턴스가
누적되고 캘린더가 멈추는 문제가 발생했습니다.

Supabase 브라우저 클라이언트를 싱글턴으로 정리하고, 구독마다 충돌하지
않는 채널 이름을 만들었습니다. Hook cleanup에서 같은 클라이언트의
`removeChannel`을 호출하도록 공통 서비스로 통합했습니다.

또한 최초 fetch와 subscribe 사이의 짧은 구간에서 변경을 놓칠 수 있으므로
`SUBSCRIBED` 직후 다시 조회하게 했습니다. 단순히 “실시간을 연결”한 것이
아니라 구독의 생성, 이벤트 유실, 중복 반영, 해제까지 수명주기로 다뤘습니다.

## Case study 3

### 사용자의 알림 설정과 일정 변경을 반영하는 예약 알림 파이프라인을 만들었습니다

일정이 생성되거나 수정되면 PostgreSQL 트리거가 기존 미발송 예약을
취소하고 사용자 설정에 맞는 새 예약을 만듭니다. pg_cron이 Edge Function을
주기적으로 호출하고, 도래한 예약은 저장된 Push Subscription을 통해
발송됩니다.

담당자가 지정된 일정은 해당 사용자에게만 예약하며, 종일 일정이나 이미
지난 알림 시각은 제외합니다. 일정 삭제는 FK의 `ON DELETE CASCADE`로
예약까지 함께 정리합니다.

Service Worker는 알림 클릭 시 기존 앱 창을 찾아 해당 날짜로 이동시키고,
열린 창이 없으면 새 창을 엽니다. 알림을 보내는 것에서 끝내지 않고 사용자가
관련 맥락으로 복귀하는 흐름까지 설계했습니다.

## Case study 4

### 구현까지 마친 네이버 캘린더 연동을 데이터 정합성 때문에 제거했습니다

PWA인 하루투두에서 홈 위젯으로 일정을 빠르게 확인하기 위해 기존에 사용하던
네이버 캘린더를 함께 활용하는 방식을 검토했습니다. 마이페이지에서 네이버
OAuth 연결과 해제를 제공하고, 사용자별 access·refresh token 저장과 만료 전
갱신, 하루투두 일정 생성 후 네이버 캘린더에 비동기로 등록하는 흐름까지
구성했습니다.

그러나 네이버의 공개 캘린더 API는 일정 추가 기능만 제공해 하루투두에서
수정하거나 삭제한 결과를 동일하게 반영할 수 없었고, 네이버에서 발생한
변경을 다시 가져올 수도 없었습니다. 생성 성공만 제공하면 시간이 지날수록
두 캘린더가 서로 다른 상태를 보여줄 수 있었습니다.

연동되어 보이지만 원본이 다른 기능은 사용자 신뢰를 해친다고 판단했습니다.
구현 비용이 이미 들었더라도 유지하지 않기로 결정하고, 마이페이지 UI,
OAuth·일정 등록 API, 서비스 호출과 개발·운영 DB의 토큰 테이블까지
제거했습니다.

## Case study 5

### 하루투두의 원본 데이터를 직접 읽는 Scriptable 홈 위젯을 만들었습니다

네이버 캘린더 연동 중단과 별개로, PWA에서는 iOS 네이티브 위젯을 직접
제공하기 어렵다는 문제는 남아 있었습니다. 외부 캘린더에 데이터를 복제하지
않고 하루투두를 단일 원본으로 유지하는 대안을 다시 설계했습니다.

iOS의 Scriptable 앱에서 동작하는 위젯 스크립트를 만들고, 인증된
`/api/widget/month`와 `/api/widget/today`를 통해 월간 일정과 오늘 할 일을
조회하도록 했습니다. API는 Bearer JWT의 사용자를 확인하고 커플 멤버십과
RLS 범위 안의 데이터만 반환합니다. 갱신 토큰은 iOS Keychain에 저장해
위젯에서도 세션을 이어갑니다.

위젯은 5분 뒤 갱신을 요청하지만 실제 실행은 iOS 스케줄링에 따르므로
실시간 동기화는 아닙니다. 이 한계를 명시하고, 일정 시간이 지나면 동일한
하루투두 원본의 최신 상태가 반영되는 보조 조회 화면으로 구현했습니다.

## AI-assisted development

### AI의 구현 속도를 제품 완성도로 연결하는 개발 시스템을 만들었습니다

AI가 코드를 생성한 사실보다 올바른 문제와 제약을 전달하고 결과를 검증하는
과정을 핵심 역량으로 정의했습니다. 실제 사용자와 문제·요구사항·MVP
우선순위를 정하고, 기능마다 화면·데이터·모바일 기준과 완료 조건을 먼저
구체화했습니다.

반복되는 판단 기준은 `AGENTS.md`, `PROJECT_RULES.md`,
`DESIGN_SYSTEM.md`에 명문화했습니다. AI는 저장소 탐색, 변경 영향 분석,
UI·Hook·Service·API·DB 구현 초안과 반복 수정에 활용했습니다. 생성된
결과는 권한, 데이터 무결성, 수명주기, 모바일 UX와 기존 구조를 기준으로
다시 검토했습니다.

구현 후에는 lint, type-check, production build와 375·768·1440px를
포함한 31개 화면 조건의 자동 렌더링 검증을 수행했습니다. 네이버 캘린더
연동처럼 이미 구현된 기능도 데이터 정합성을 보장할 수 없으면 UI, API,
서비스와 DB에서 제거했습니다.

### 사람과 AI의 책임을 구분했습니다

#### 직접 책임진 판단

- 실사용자 문제, 요구사항과 MVP 우선순위
- 모바일 UX 방향과 기능별 완료 조건
- 데이터 신뢰성, 보안과 기존 기능 영향 검토
- 구현 결과 승인·보류·제거와 출시 판단

#### AI로 가속한 작업

- 저장소 탐색과 변경 영향 범위 분석
- 여러 계층의 구현 초안과 반복적인 수정
- 테스트·검증 스크립트와 문서화 보조
- 기술 대안 비교와 누락 위험 점검

이 프로젝트에서 보여주려는 역량은 타이핑한 코드의 양이 아니라, AI가
일관된 결과를 만들 수 있는 개발 맥락을 설계하고 그 결과를 실제 서비스
품질로 수렴시킨 과정입니다.

## Retrospective

### 잘한 점

- 기능보다 핵심 사용자 행동을 먼저 정의했다.
- 권한과 무결성을 프론트엔드가 아닌 DB까지 내려서 보장했다.
- 실제 장애를 계기로 Realtime 수명주기를 공통화했다.
- 모바일 환경을 후속 대응이 아니라 초기 설계 기준으로 두었다.

### 개선할 점

- 자동화 테스트가 유틸리티에 집중되어 핵심 사용자 흐름의 회귀 방지가 약하다.
- Hook이 데이터 접근과 도메인 로직을 함께 맡는 부분을 점진적으로 분리해야 한다.
- 실제 사용자 행동을 판단할 제품 지표와 사용성 테스트가 더 필요하다.
- 정기 알림 함수의 호출 주체와 중복 실행 방어를 보완해야 한다.

3. 알림 발송 성공률과 핵심 행동 전환을 관찰할 운영 지표를 정리한다.
