# 제품 개발 단계 전환 설계

**작성일:** 2026-06-14  
**상태:** 승인 대기  
**작성 목적:** 하루투두를 MVP 검증 단계에서 정식 제품 개발(Product Growth) 단계로 전환하기 위한 원칙, 기준, 실행 계획 정의

---

## 1. 전환 배경

하루투두는 커플/부부 2인을 위한 공유 투두 + 캘린더 PWA로 출발했다. 초기 CLAUDE.md와 백로그 문서는 "앱스토어 등록 전 MVP 검증"을 목표로 작성됐으며, 아래 원칙들이 중심이었다.

- MVP에 꼭 필요한가를 먼저 묻는다
- MVP 외 기능은 선구현하지 않는다
- 변경 범위를 최소화하고 빠르게 검증한다

이 원칙들은 초기 방향 유지에 효과적이었다. 그러나 현재 구현 상태를 보면, 이미 MVP 범위를 넘어선 기능들이 상당수 존재한다.

**MVP 초과 구현 현황:**
- 푸시 알림 (Supabase Edge Functions: morning-summary, evening-reminder, event-reminder, notify-partner)
- 알림 설정 UI (useNotificationSettings, PushBanner)
- 분석 이벤트 추적 (analyticsService, trackEvent)
- 커스텀 그룹 (최대 5개, 인라인 생성, 마이페이지 삭제)
- Dev/Prod Supabase 환경 분리
- Vitest 단위 테스트 인프라
- CI/CD GitHub Actions (engineering-harness-phase1 설계)
- CalendarPickerSheet, EventDaySheet 등 고도화된 UI 컴포넌트

이는 "MVP 외 기능 선구현 금지" 원칙이 현실에서 이미 통용되지 않고 있음을 뜻한다. 원칙을 강화할 것인지, 현실을 반영해 기준을 갱신할 것인지 결정이 필요하다.

**전환의 이유:**
기존 MVP 원칙을 그대로 유지하면, 실제 구현된 기능들이 "정식 원칙 밖" 상태로 방치돼 관리 기준이 불명확해진다. 제품이 성장 단계로 진입한 현실에 맞는 기준이 필요하다.

## 3. MVP 규칙의 문제와 유지 가치

### 유지할 가치가 있는 MVP 원칙

| 원칙 | 유지 이유 |
|------|-----------|
| 제품 가치를 먼저 묻는다 | 기능이 많아져도 핵심 가치 흐림 방지 |
| 변경 범위를 최소화한다 | 대규모 리팩토링은 여전히 위험 |
| 사용자 승인 없는 DB 스키마 변경 금지 | 데이터 무결성 보호 |
| 모바일 퍼스트 품질 기준 | 서비스의 본질적 플랫폼 |
| 디자인 토큰 우선 사용 | 일관성 유지 비용 절감 |
| `any` 타입 금지 | 타입 안정성 보장 |
| Supabase 직접 import 금지 (services 경유) | 아키텍처 일관성, 이식성 |

### 현실과 충돌하는 MVP 원칙 (수정 필요)

| 현재 원칙 | 문제 | 제안 |
|-----------|------|------|
| "MVP에 꼭 필요한가?" | 이미 MVP 초과 상태 — 판단 기준이 무의미 | "제품 가치와 사용성에 기여하는가?"로 전환 |
| "MVP 외 기능 선구현 금지" | 푸시 알림, 분석 등이 이미 구현됨 | "미승인 구현 금지"로 범위 재정의 |
| "범위 밖 요청은 백로그로" | 성장 단계에서는 일부 기능이 빠르게 검토 가능 | 우선순위 기준을 제품 가치 기여도로 재설정 |
| "출시 가능한 수준을 점진적으로" | 이제 정식 제품 기준 적용 필요 | 완료 정의(Definition of Done)를 명문화 |

## 4. Product Growth Stage 정의

### 단계 정의

**MVP Stage (이전):** 핵심 기능 검증, 빠른 반복, 최소 범위 구현, 조기 출시 우선

**Product Growth Stage (현재 전환 대상):** 기능 검증을 마친 제품에 대해 사용성 고도화, 안정성, 데이터 기반 의사결정, 지속 가능한 개발 방식을 확립하는 단계

### 이 단계에서 달라지는 것

| 항목 | MVP Stage | Product Growth Stage |
|------|-----------|----------------------|
| 기능 판단 기준 | MVP 여부 | 사용성 기여도 + 기술 완성도 |
| 코드 품질 기준 | 동작하면 OK | lint 통과 + 테스트 + 빌드 모두 통과 |
| 완료 정의 | 화면이 보이면 완료 | 14개 기준 모두 통과 |
| 기술 부채 처리 | 나중에 | 정의된 품질 게이트 도입 |
| 분석/지표 | 없음 | 핵심 지표 추적 + 의사결정 반영 |
| 문서화 | 최소 | 설계 의도와 결정 기록 |

### 이 단계에서 변하지 않는 것

- 커플 2인 공유 투두/캘린더라는 핵심 가치
- 모바일 PWA 우선
- 과한 커플 감성 지양, 실용성 우선
- 사용자 승인 없는 스키마 변경 금지
- Supabase 직접 import 금지 원칙

## 5. 제품 개발 원칙

### 제품 관점

1. 이 변경이 "오늘 할 일 파악", "파트너 구분", "반복 사용 부담 감소", "모바일 PWA 품질" 중 하나 이상에 기여하는가?
2. 기능 추가보다 기존 기능의 완성도가 우선이다. 반쪽짜리 기능 10개보다 완성된 기능 5개가 낫다.
3. 커플이 함께 쓰는 맥락에서 자연스러운가? 1인 사용에 최적화된 UX는 지양한다.
4. 데이터 기반으로 판단한다. 감각적 판단과 분석 지표를 함께 사용한다.

### UX 관점

1. 앱을 열자마자 오늘 해야 할 일이 보여야 한다 (5초 내).
2. 주요 액션은 한 손으로 조작 가능한 위치에 있어야 한다.
3. 빈 상태, 로딩 상태, 에러 상태 각각에 명확한 다음 행동이 있어야 한다.
4. 새 기능 추가 시 기존 흐름을 복잡하게 만들어서는 안 된다.

### 기술 관점

1. 동작하는 코드보다 검증된 코드를 우선한다. lint + 테스트 + 빌드 모두 통과해야 완료다.
2. 빠른 구현과 기술 부채 사이의 트레이드오프를 명시적으로 기록한다.
3. 서비스 계층(`lib/services/`)을 경유하지 않는 Supabase 직접 접근은 금지다.
4. 스키마 변경은 마이그레이션 파일로 관리하고 사용자 승인을 받는다.

## 6. 기능 기획 기준 (14개 체크리스트)

새 기능 또는 주요 변경 전 아래 14개 항목을 확인한다. 전부 통과하지 못하면 기획을 보완하거나 보류한다.

1. **핵심 가치 기여**: "오늘 할 일 파악", "파트너 구분", "반복 사용 부담 감소", "PWA 품질" 중 하나 이상에 직접 기여하는가?
2. **사용 빈도**: 매일 또는 주 3회 이상 자연스럽게 사용될 기능인가?
3. **커플 맥락**: 1인 사용이 아닌 커플 2인이 함께 쓸 때 가치가 있는가?
4. **기존 흐름 침해 여부**: 기존 핵심 흐름(투두 CRUD, 캘린더 탐색)을 복잡하게 만들지 않는가?
5. **완성도 선행 확인**: 기존 기능 중 미완성 상태인 것을 먼저 완성하는 것이 더 가치 있지 않은가?
6. **모바일 UX 가능성**: 375px, iOS Safari, Android Chrome에서 자연스럽게 동작하는 UX가 설계 가능한가?
7. **터치 조작성**: 44px 이상 터치 타깃과 한 손 조작이 가능한가?
8. **빈/로딩/에러 상태**: 세 가지 상태 각각의 UX가 설계에 포함돼 있는가?
9. **스키마 변경 여부**: DB 변경이 필요하다면 사용자 승인 계획이 있는가?
10. **RLS/보안 검토**: 새 데이터가 다른 커플에게 노출될 위험은 없는가?
11. **서비스 계층 설계**: `lib/services/`에 적합한 서비스가 있거나 새로 만들 계획이 있는가?
12. **타입 안정성**: `any` 없이 도메인 타입으로 표현 가능한가?
13. **분석 추적 가능성**: 이 기능의 사용 여부를 이벤트로 추적할 수 있는가?
14. **롤백 가능성**: 기능이 실패하거나 사용자가 싫어할 때 빠르게 되돌릴 수 있는가?

## 7. 완료 정의 (Definition of Done, 14개 기준)

기능 구현 완료는 아래 14개 기준을 모두 통과해야 한다. PR 병합 또는 배포 전 체크리스트로 사용한다.

1. **타입 오류 없음**: `npm run type-check` (`tsc --noEmit`) 통과
2. **린트 통과**: `npm run lint` 에러 0개 (경고는 허용하되 신규 경고 추가 금지)
3. **빌드 성공**: `npm run build` 성공 (Next.js 프로덕션 빌드)
4. **단위 테스트 통과**: 관련 순수 함수 Vitest 테스트 작성 및 통과 (CI 구성 후 적용)
5. **모바일 검수 완료**: 375px 기준 Chrome DevTools 또는 실기기에서 핵심 흐름 확인
6. **빈 상태 처리**: 데이터가 없는 경우 적절한 안내 문구와 CTA 존재
7. **로딩 상태 처리**: 비동기 요청 중 스피너 또는 스켈레톤 표시
8. **에러 상태 처리**: 실패 시 재시도 또는 이동 경로 제공
9. **safe area 대응**: 하단 탭, 키보드 노출 시 주요 UI 가려지지 않음
10. **터치 타깃**: 모든 인터랙티브 요소 44px 이상
11. **RLS 확인**: 새 테이블/쿼리가 있다면 다른 커플 데이터 접근 불가 검증
12. **서비스 계층 경유**: UI 컴포넌트에서 Supabase 직접 import 없음
13. **any 타입 없음**: 도메인 타입 또는 명시적 제네릭으로 대체
14. **디자인 토큰 준수**: 임의 색상/spacing/radius/shadow 하드코딩 없음

## 8. 기술 설계 기준

### 아키텍처 원칙

- **서비스 계층 필수**: 모든 Supabase 접근은 `lib/services/` 경유. UI 컴포넌트와 hooks에서 직접 import 금지.
- **도메인 타입 우선**: `types/domain/` 타입을 컴포넌트 props/state 타입으로 사용. raw schema row (`Tables<...>`) 직접 노출 금지.
- **플랫폼 이식성**: `lib/services/`, `lib/utils/`, `types/domain/`, `store/`에 `next/*` import 금지.
- **단방향 의존성**: services ← hooks ← components. 역방향 의존 금지.

### 데이터 모델 원칙

- 스키마 변경은 반드시 마이그레이션 파일(`supabase/migrations/`)로 관리.
- 컬럼 추가/삭제/타입 변경은 사용자 승인 후 진행.
- 신규 테이블에는 RLS 정책을 반드시 함께 작성.
- `gen_random_uuid()`를 사용 (PG15 호환, `uuid_generate_v4()` 금지).

### 상태 관리 원칙

- 서버 상태: Supabase 쿼리 + Realtime.
- 클라이언트 전역 상태: Zustand (`store/`).
- 로컬 UI 상태: `useState`, `useReducer`.
- SSR/hydration 충돌 금지: `localStorage` / `window.*` 접근은 `useEffect` 내에서만.

### 코드 품질 원칙

- `any` 타입 금지.
- ESLint 에러 0 상태 유지 (신규 코드는 에러 없이 작성).
- 주석은 WHY가 비명확할 때만 작성.
- 함수/컴포넌트 크기: 단일 책임 원칙, 100줄 초과 시 분리 검토.

### 성능 원칙

- Realtime 구독은 멱등 처리(중복 이벤트 무시).
- 불필요한 리렌더 방지: `useCallback`, `useMemo`는 실제 성능 문제가 있을 때만 사용.
- 이미지/아이콘: Next.js Image 또는 lucide-react 사용 (외부 CDN 임의 추가 금지).

## 10. 데이터·보안·운영 기준

### 데이터 보안

- **RLS 필수**: 모든 테이블에 Row Level Security 활성화. 신규 테이블 추가 시 RLS 정책 동시 작성.
- **커플 격리**: 모든 쿼리는 `couple_id` 범위 내에서만 접근 가능해야 한다. 다른 커플 데이터 크로스 접근 불가.
- **Supabase SERVICE_ROLE_KEY**: 서버 전용 (Edge Functions, Route Handlers). 클라이언트 번들에 절대 포함 금지.
- **인증 필수 경로**: `app/(main)/layout.tsx`에서 세션 + 프로필 + 커플 존재 검증.

### 환경 관리

- **Dev/Prod 분리 유지**: `.env.local` = dev Supabase, Vercel 환경변수 = prod Supabase.
- **마이그레이션 흐름**: `npm run db:link:dev` → `npm run db:push` (dev 검증) → `npm run db:link:prod` → `npm run db:push` (prod 배포).
- **환경변수 문서화**: `.env.local.example`을 항상 최신 상태로 유지.

### 운영 기준

- **회원탈퇴 미구현 시 주의**: 현재 대시보드 수동 삭제는 JWT 즉시 무효화를 보장하지 않음 (최대 1시간 잔존). 회원탈퇴 기능 구현 시 `admin.deleteUser(SERVICE_ROLE_KEY)`를 사용해야 즉시 무효화 가능.
- **커플 해제 미구현**: 커플 해제 시 데이터 처리 정책(투두/일정 귀속) 사전 결정 필요.
- **Realtime 구독 관리**: 컴포넌트 언마운트 시 반드시 구독 해제. 멱등 처리 유지.
